## 2. Описание

Разработайте CLI-утилиту, которая читает NGINX-логи из локального файла, набора файлов по
glob-маске или URL, разбирает записи, фильтрует их по датам и формирует статистический отчет.

Пример строки лога:

```text
93.180.71.3 - - [17/May/2015:08:05:32 +0000] "GET /downloads/product_1 HTTP/1.1" 304 0 "-" "Debian APT-HTTP/1.3"
```

Из нее нужно получить IP-адрес, дату и время, HTTP-метод, ресурс, протокол, код ответа и размер
ответа. Метод, ресурс и протокол хранятся как отдельные поля.

Утилита должна корректно работать с большими файлами, поврежденными строками и ошибками
пользовательского ввода:

- работа с файлами, URL и другими недоверенными входными данными
- потоковая обработка без загрузки всего источника в память
- устойчивый разбор строк фиксированного формата
- разделение ошибок запуска и ошибок отдельных записей
- контракт CLI, предсказуемые exit codes и форматы отчетов
- расчет top-N, распределений и перцентиля p95

## 3. Требования к реализации

Структура решения не задается. Можно оставить код в одном файле или разделить его на модули -
выберите вариант, который удобно развивать и тестировать. Если точка входа переносится из
`src/main.py`, обновите команды запуска и GitLab CI.

Пример запуска:

```bash
make run ARGS="--path logs/*.log --format markdown --output report.md --from 2025-03-01"
```

Поддерживаемые параметры:

| Параметр         | Описание                                                     |
| ---------------- | ------------------------------------------------------------ |
| `--path`, `-p`   | Локальный файл, glob-маска или URL                           |
| `--format`, `-f` | Формат отчета: `json` или `markdown`                         |
| `--output`, `-o` | Путь, по которому нужно сохранить отчет                      |
| `--from`         | Начальная дата периода в формате `YYYY-MM-DD`, включительно  |
| `--to`           | Конечная дата периода в формате `YYYY-MM-DD`, включительно   |

Значение по умолчанию для `--format` выберите самостоятельно и опишите в README. Параметр
`--output` обязателен в базовой части задания. Формат файла должен соответствовать расширению:
`.json` для JSON и `.md` для Markdown.

Источники и обработка данных:

- поддерживаются файлы с расширениями `.log` и `.txt`
- glob-маска должна раскрыться во все подходящие файлы, каждый из них учитывается в отчете
- отсутствие локального файла и пустой результат glob-маски считаются ошибкой использования
- URL должен быть доступен и возвращать успешный HTTP-ответ
- локальные и удаленные источники читаются построчно, без загрузки всего содержимого в память
- каждая непустая корректная строка преобразуется в модель `LogRecord`
- поврежденная строка пропускается, а в stderr записывается предупреждение
  `WARN: skipped malformed log line`, обработка остальных строк продолжается

Фильтрация по датам:

- без `--from` и `--to` учитываются все корректные записи
- только `--from` задает открытую верхнюю границу
- только `--to` задает открытую нижнюю границу
- при двух границах должно выполняться `from < to`
- обе указанные даты входят в период целиком

Статистика по отфильтрованным корректным записям включает:

- общее число запросов
- распределение кодов ответа
- десять наиболее популярных ресурсов, отсортированных по убыванию числа запросов
- средний, максимальный размер ответа и p95, дробные значения округляются до двух знаков

При равном числе запросов задайте стабильное дополнительное правило сортировки ресурсов и
зафиксируйте его в README и тестах.

Метод расчета p95 необходимо описать в README или тестах. Он должен давать воспроизводимый
результат. Например, можно использовать nearest-rank: отсортировать значения и выбрать элемент с
однобазовым индексом `ceil(0.95 * N)`. При таком способе для размеров `100, 200, 300, 400, 500`
p95 равен `500`.

Отчеты:

- JSON содержит поля `files`, `totalRequestsCount`, `responseSizeInBytes`, `resources` и
  `responseCodes`
- `responseSizeInBytes` содержит `average`, `max` и `p95`
- Markdown содержит те же данные, заголовок и таблицы
- отчет сохраняется в файл
- существующий output-файл не перезаписывается и считается ошибкой использования

Exit codes:

| Код | Значение                                                  |
| --: | --------------------------------------------------------- |
| `0` | Успешное завершение                                       |
| `1` | Непредвиденная внутренняя ошибка                          |
| `2` | Некорректное использование или ожидаемая ошибка источника |

К коду `2` относятся, например, отсутствие `--path`, неподдерживаемый формат, неверная дата,
`from >= to`, отсутствие файла, пустой glob, недоступный URL, HTTP 404, неподдерживаемое
расширение, несоответствие расширения отчета формату и уже существующий output-файл.

### MR1 - CLI и источники логов

Реализуйте:

### MR2 - парсер и статистика

Поддержите формат строки:

```text
$remote_addr - $remote_user [$time_local] "$request" $status $body_bytes_sent "$http_referer" "$http_user_agent"
```

Добавьте:

- разбор строки в `LogRecord` с отдельными полями метода, ресурса и протокола

Парсер и расчет статистики не должны зависеть от конкретного способа получения строк. Ошибка в

Добавьте:

- документированные exit codes `0`, `1` и `2`
- blackbox/e2e-тесты запуска CLI в отдельном процессе

## 5. Тесты

Готовых тестов в шаблоне нет. Создавайте файлы `_test.go` рядом с тестируемыми пакетами и
используйте стандартный пакет `testing`. Для однотипных сценариев применяйте табличные тесты и
именованные под-тесты через `t.Run`.

Проверьте:

- отсутствие `--path`, `--format xml` и `from >= to` приводят к exit code `2`
- читаются локальный файл и URL, а glob включает в отчет все подходящие файлы
- отсутствующий файл, пустой glob и HTTP 404 приводят к exit code `2`
- эталонная строка разбирается в корректные поля `LogRecord`
- поврежденная строка пропускается, warning записывается, программа продолжает работу
- фильтр работает только с `--from`, только с `--to`, с обеими и без границ
- обе границы периода включаются целиком
- коды `200, 200, 404, 500, 500, 500` группируются как `200: 2`, `404: 1`, `500: 3`
- ресурсы сортируются по убыванию количества, результат ограничивается десятью строками
- для размеров `100, 200, 300, 400, 500` получаются average `300`, max `500`, p95 `500`
- JSON-отчет валиден и содержит все обязательные поля
- Markdown-отчет содержит заголовок и таблицы
- output-файл с неверным расширением отклоняется
- существующий output-файл не изменяется и приводит к exit code `2`
- неожиданная внутренняя ошибка приводит к exit code `1`
- e2e-тест проверяет успешный запуск и созданный отчет через отдельный процесс

Для URL-тестов используйте `httptest.Server` или передавайте настроенный `http.Client`. Тесты не
должны зависеть от интернета и готового сервера из шаблона. Для файлов используйте `t.TempDir`.
Для точной проверки exit codes сначала соберите бинарник, затем запустите его через `os/exec`:
`go run` не обязан передавать вызывающему процессу исходный код завершения программы.

Потоковость проверяйте управляемым `io.Reader`; тесту не нужно создавать гигантский файл или
измерять память процесса.

Команда `make test` запускает стандартный `go test` и формирует:

- `coverage.out` с профилем покрытия;
- `coverage.html` для просмотра в браузере.

`make test-race` отдельно включает race detector. Для него локально нужен Go с поддержкой CGO и
C-компилятор.

## 6. Ограничения и советы

Ограничения:

- не добавляйте GUI, веб-интерфейс, веб-сервис или realtime-дашборд;
- не подключайте базу данных, ELK, Grafana или ClickHouse;
- не добавляйте авторизацию и поддержку всех существующих форматов логов;
- не требуется идеально точный streaming p95 для данных, которые не помещаются в память;
- не загружайте исходный лог целиком через `io.ReadAll` или аналогичный код;
- не перезаписывайте существующий отчет без явного требования задания;
- готовый `cmd/log-server` не нужно изменять и покрывать тестами.

Советы:

- разделите разбор аргументов, открытие источников, парсинг строк, агрегацию и рендеринг отчета
- передавайте между слоями `io.Reader`, чтобы сохранить потоковую обработку
- для построчного чтения используйте `bufio.Scanner` с явно увеличенным буфером или
  `bufio.Reader`, стандартный лимит `Scanner` может быть недостаточен для длинного User-Agent
- проверяйте параметры до начала длительного чтения
- разбирайте даты через `time.Parse`, включая числовое смещение часового пояса NGINX
- задавайте timeout у `http.Client` и всегда закрывайте `response.Body`
- создавайте HTTP-запросы через `http.NewRequestWithContext`
- передавайте logger или `io.Writer` для предупреждений вместо глобального логгера
- добавляйте контекст к ошибкам через `%w`, а ожидаемые ошибки проверяйте с `errors.Is`
- создавайте output через `os.OpenFile` с `O_CREATE|O_EXCL|O_WRONLY`
- записывайте отчет только после успешного чтения и построения статистики
- сортируйте результаты явно, чтобы отчет не зависел от порядка `map` или файловой системы
- используйте `t.TempDir`, `httptest.Server` и `exec.CommandContext` в тестах
